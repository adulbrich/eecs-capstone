# A revisit waits for its loader rather than painting the last visit's data

Amended on 2026-09-25 by [#499](https://github.com/adulbrich/eecs-capstone/issues/499): the Consequences said the routes seeding state from loader data were keyed, and a sweep found six that are not. They now carry the census of every such seed in four classes, and record that the six rely on this option by decision.

`src/router.tsx` sets `defaultStaleReloadMode: "blocking"`, so a stale route match waits for its reload instead of painting cached `loaderData` and revalidating behind it. `defaultStaleTime` is 0, which makes every revisit stale, and the default `"background"` meant every navigation away from a save landed on a frame built from pre-edit data: a list flashed the old row, and an edit form whose inputs are `useState(record.field)` seeded from that frame and never recovered, because a `useState` initializer does not re-run when props change. That second half is a write risk rather than a display one, since a staff member reopening such a form sees stale values and saves them back over a colleague's edit. The alternative, `router.invalidate({ sync: true })` before each `navigate()`, was measured and works, and was rejected because it has to be remembered at each of seven call sites and the eighth silently restores the bug; plain `invalidate()` fixes nothing here, because it revalidates in the background and its promise resolves before any reload lands. The cost is accepted and felt by real users: a revisit now behaves like a first visit, the previous page stays on screen until the loader resolves, and the app sets no `defaultPendingComponent`, so nothing marks the wait at all. The router's 1s `defaultPendingMs` only applies to a route with a pending component. Decided 2026-09-17 in #474.

## Consequences

Seeding component state from loader data is only correct while the router blocks, and a seed raises two questions that the first version of this section ran together. The first is whether it needs a resync for its own writes. A control that is the only writer of its field, stays mounted across its own `await router.invalidate()`, and holds what staff just typed does not, which is why #474 left the mentor count, `CustomLineActions` and `StaffProgramSection` alone. The second is whether it survives mounting on a stale frame, and that is the one this decision answers: under `"background"` a revisit paints the pre-edit record, the seed captures it, and the reload that lands a moment later cannot reach it. That is a write risk rather than a display one, because the control saves what it holds: reopen it, see the pre-edit values, and save them over the newer edit. The census below is from 2026-09-25 (#499), and `src/test/loader-seed-scan.test.ts` holds every once-only initializer in `src/` that is not a plain literal to it, each with its class and reason, so a new one fails until somebody classifies it here.

Class A is seeded from loader data with no key and no resync: six components holding eight seeds. `ProjectForm`'s `defaultValues` on `/projects/$projectId/edit`, `InventoryForm`'s on `/inventory/$itemId/edit`, `RoleSelect`'s `useState(initialRole)` on `/admin/users/$userId`, `StaffProgramSection`'s programs, team count and team-full flag on `/projects/$projectId`, `CustomLineActions`'s sourcing note on `/admin/inventory/requests`, and `MentorControls`'s team count on `/admin/mentors`. The role is the sharpest of them, since what a stale save writes back is somebody's role.

Class B is keyed on the record, so a record that differs remounts the seeds: `/admin/programs/$programId` on `String(program.updatedAt)`, which `updateProgramAs` bumps, and `/admin/categories/$categoryId` on its seeded values, because the `categories` table has no `updatedAt` and a column added to feed a React key would be a schema change in service of a render detail. Those keys are the second line of defence rather than decoration: with this option reverted to `"background"` the stale frame still paints, but the background reload lands a record whose key differs and the form remounts onto it. That was measured on the program form, whose reopen-after-save assertion closes the "staff create a program, add an instructor, then rename it" test in `admin-catalog.e2e.test.ts`: reverting the router option alone leaves it green, and reverting the key with it turns it red. The category form is keyed on the same reasoning and has no such assertion, so that half is argued rather than run.

Class C is seeded once and resynced by an effect: `InstructorManager` runs `useEffect(() => setInstructors(initial), [initial])`, and `useDebouncedDraft` owns its resync deliberately, its docstring naming this failure for a search box. Class D is once-only but not seeded from loader data, and out of scope: `StaffProposerSection` seeds from a record its panel fetches in an effect, `ProposerPicker` captures `useState(value)` at mount on purpose, `/profile` seeds two `useState` and three uncontrolled `defaultValue` from route context, and `LocalTime` is display only. The scan's census carries the rest of class D, each with its reason.

The six class A sites depend on `defaultStaleReloadMode: "blocking"` by decision rather than by omission, because every alternative discards somebody's in-progress edit. A key on `projects.updatedAt` fires on any write to the project, so a staff status transition or program move would remount a proposer's open form and throw away their edit for a change to none of the fifteen fields it seeds; status and program writes have to keep bumping that column for the "Recently updated" sort (#475). A key on a composite of the seeded values fires only on a real conflict, but it remounts the whole subtree, open dialogs and the AI review panel's state with it, and the composite drifts silently when a field is added. A resync effect has the same trigger as that composite and overwrites least, so it is the designated remedy if this option is ever reverted, or if a route opts out with `staleReloadMode: "background"`: the pattern in `src/components/instructor-manager.tsx` and `src/lib/use-debounced-draft.ts`, one line with a primitive dependency on each of the four `useState` sites, the program ids joined into a string for `StaffProgramSection`. The two TanStack Form sites need more care. `initial` is an object literal rebuilt on every render, so the effect wants a memo or a value comparison rather than the object as its dependency, and `form.reset()` clears every field where `form.resetField()` can touch only the ones that moved.

`remountDeps` cannot stand in for a key at all: it sees `search`, `params` and `loaderDeps`, never loader data. The stay-on-page pattern is unaffected, because a component that stays mounted across `await router.invalidate()` re-renders from the new data and its seed is the question of resyncing its own writes, not of a stale mount. A route that measurably needs the instant paint can opt back in with `staleReloadMode: "background"` on itself, and then owns the freezing problem for any seed it holds, starting with the resync above for a class A one; none does today. The heaviest loader here, `/admin/projects`, returns 28 KB across two server functions in about 55 ms, so the wait is the round trip rather than the query, and a `defaultPendingComponent` is the answer if that round trip ever reads as a hang.
