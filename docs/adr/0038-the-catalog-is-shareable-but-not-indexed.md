# The catalog is shareable but not indexed

Every catalog page carries `<meta name="robots" content="noindex, follow">` while `public/robots.txt` stays fully permissive, and the two halves are one decision rather than an inconsistency. The project and inventory listings and their detail pages are deliberately absent from search results: a project detail page carries a contact name and a hand-typed address that the proposer chose to publish to a reader, not to a scraper working from a search index, and the archive holds hundreds of legacy imports that would outrank the current term's projects for any query naming the program. Tightening `robots.txt` to match was rejected, and would have been the obvious move: a `Disallow` is a ban on fetching, and the preview scrapers that matter here (Twitterbot, facebookexternalhit, LinkedInBot, Slackbot, Discordbot) all honour it, so it would have silently destroyed the link previews this same change exists to create. `noindex` is read only by indexers and leaves scrapers alone, which is the only mechanism that separates the two concerns, and the separation is the point: a proposer pasting their project into Teams gets a title, a summary and a brand card, while the same page never appears in a search result. The landing page and the privacy page stay indexable, because a program wants to be found; only the catalog underneath them does not. Decided 2026-09-20 in #498.

## Consequences

Search engines are the audience this gives up, and giving them up is what makes the metadata worth having at all: chat unfurls are now the only consumer of the `og:` tags, which is also why #533 (a per-project card, so two project links do not unfurl with the same image) is worth doing and a `sitemap.xml` is not. The tags have to survive server rendering, since a crawler runs no JavaScript and a meta tag added at hydration is not there; the `noindex` and the `og:` tags are asserted against an anonymous SSR fetch for that reason. Nothing here reduces what an anonymous reader can fetch: `contactName` and `contactEmail` remain in `projectDetailView`, the project form tells proposers both fields are optional and public, and a scraper that already has a URL is unaffected by either lever. If that exposure is the real concern, it is a change to the public payload and belongs in its own issue rather than here. Reversing this decision is one constant: `NOINDEX` in `src/lib/social-meta.ts` is the single spelling, applied by nine routes. Reversing it is not free in the other direction, though, because pages that have been out of the index for a term do not return to it the moment the tag goes.
