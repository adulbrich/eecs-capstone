# A save does not wait for its AI refresh

Editing, publishing, archiving or restoring a project that ends up published or archived starts its embedding and social summary refresh and returns without waiting for it; `refreshProjectInBackground` in `src/server/_internal/project-refresh.ts` is the one place that starts them, and both call sites in `projects.ts` go through it. Before this, `updateProjectAs` and `commitTransition` awaited both model calls after the commit, and on 2026-09-23 a stalled Mantle call held a staff save's response for 301 s, undici's header timeout, while the row had long since committed: the button sat on "Saving...", the toast never came, and the only record was `Social summary failed ... fetch failed` five minutes later. Approving was unaffected because `approved` is not an embeddable status. Timeouts alone would have kept the save waiting on the model for as long as the timeout, so they bound the work instead of the response: 60 s on the Mantle fetch and 30 s on the Titan call, against a slowest save of 2.3 s across the week of ALB logs before. The Mantle bound is in the shared adapter, so it also caps the AI review and the scope assessment, which the user does wait on; their slowest that week were 4.5 s and 5.3 s. The response now says the edit committed and nothing about the refresh, which was already best effort: both refreshes swallow their failures, and `scripts/backfill-embeddings.mjs` and `scripts/backfill-social-summaries.mjs` sweep up a stale hash. Refreshes for one project run on a task in the order they are started, just after each commit, and each reads the row when it runs, so the last one reads the last committed text. Two tasks can interleave, and answering early makes that likelier, since a second save no longer waits behind the first's model call; so each write holds only while the row still carries the text the model was shown (`rowStillReads`), and the summary's also while the stored summary is the one it read. Regenerate guards its write on the same text, so whichever of the two read the current text is the one that lands. A write that loses reports `superseded` (Regenerate, `changed`), and the edit that beat it has started its own refresh. The production backfills still write by id alone: a sweep racing an edit can store a vector or summary of the older text, which leaves a hash that no longer matches and so is redone by the next sweep or edit. Every refresh logs one line with both outcomes and its duration, which is how to tell from CloudWatch whether a given save's refresh applied. A deploy that stops a task mid-refresh loses that refresh the same way; the backfill is again the answer. Integration tests read what a refresh wrote only after `settleProjectRefreshes()`, and `setup.integration.ts` settles before every truncate. Decided 2026-09-23.
