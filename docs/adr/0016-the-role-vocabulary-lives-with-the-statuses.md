# The role vocabulary lives with the statuses, not beside the staff predicate

`USER_ROLES` is in `src/lib/vocabularies.ts`, next to the three status tuples, rather than in `src/lib/viewer.ts` next to `STAFF_ROLES` where the domain question already lives. The reason is `src/lib/__tests__/vocabulary-scan.ts`: it discovers what to look for by parsing `vocabularies.ts` and takes every exported `as const` array of string literals, so a tuple placed there is scanned the moment it lands and a tuple placed anywhere else needs the scan taught a second file. That was not a theoretical gain. The list was written out five times under `src/`, and the scan named all five on its first red run, including a `type Role = "user" | "instructor" | "admin"` union in each of the two user admin components that #274 had not found by reading the code. It reads `src/` and nothing else, so the sixth copy, in `scripts/seed-dev.ts`, had to be found by hand and will stay findable only by hand. The split that results is worth stating plainly: `vocabularies.ts` holds the legal values, `viewer.ts` holds the questions asked about them.

[ADR-0014](./0014-status-vocabularies-live-in-src-lib.md) put the status tuples in `src/lib` so that a client-safe module naming a status would not drag `drizzle-orm` into the bundle. That argument does not carry a role anywhere, because `user.role` is `text` owned by Better Auth's admin plugin and there is no `pgEnum` to derive from in the first place. What follows from the missing column constraint is that the tuple is the only anchor a role has: a status the app misspells is a row Postgres rejects, and a role the app misspells is a row it accepts and nothing selects. So the scan is not a second line of defence here the way it is for statuses. Inside `src/` it is the only one, and outside it there is nothing at all.

## Consequences

`STAFF_ROLES` is held to the vocabulary by `as const satisfies readonly UserRole[]` rather than derived from it, because which roles carry staff powers is a judgement and a fourth role must not become staff by arriving. The same `satisfies` appears on the two role names in `admin()` in `src/lib/auth.ts`, written on the literals rather than passed as the tuple: the plugin types `defaultRole` as `string` and `adminRoles` as `string | string[]`, so a readonly tuple is not assignable, and handing it the whole vocabulary would make every role an admin. Both spellings buy the same thing, which is that a role renamed in the tuple fails to compile at those three sites rather than quietly stripping powers.

That promise stops there, and deliberately. `isAdmin` still reads `viewer.role === "admin"`, and `Viewer.role` is still `string | null | undefined`, because the column is `text` that Better Auth owns and a row really can hold a string no tuple names. Narrowing the field to `UserRole` would make the type say something about the database that is not true. So a rename remains a change somebody has to sweep, and what the tuple buys is that the sweep has one list to work from and three sites that fail loudly if it is missed.

There is one order and no reader's order beside it. `PROJECT_STATUSES_IN_DISPLAY_ORDER` exists because a reader genuinely wants a different order for the statuses, putting `changes_requested` beside `submitted` as the step back out of review where the tuple lists it as one of two outcomes. Nothing like that was at stake here: the two orders this replaced disagreed by accident, neither of them anyone's judgement about what a reader wants, so the admin filter, the role select on the user detail page and the analytics breakdown now all read the tuple directly. The visible effect is that the analytics chart lists `user, instructor, admin` where it listed `admin, instructor, user` before, which is a change to what a reader sees under a `refactor` commit and is called out in the pull request for that reason.

The eleven `makeUser` helpers in the integration suites took `UserRole` too, even though the scan skips `__tests__` and would never have flagged them. Its reason for skipping does not cover them: it cannot tell a test's case list from its expected value, and a parameter type annotation is neither. It is a copy with no job, so it went. What stays hand-written in those files is the role each test seeds, which is the fixture rather than the vocabulary.
