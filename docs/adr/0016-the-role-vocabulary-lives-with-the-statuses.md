# The role vocabulary lives with the statuses, not beside the staff predicate

`USER_ROLES` is in `src/lib/vocabularies.ts`, next to the three status tuples, rather than in `src/lib/viewer.ts` next to `STAFF_ROLES` where the domain question already lives. The reason is `src/lib/__tests__/vocabulary-scan.ts`: it discovers what to look for by parsing `vocabularies.ts` and takes every exported `as const` array of string literals, so a tuple placed there is scanned the moment it lands and a tuple placed anywhere else needs the scan taught a second file. That was not a theoretical gain. The list was written out five times before this, and the scan named all five on its first red run, including two `type Role = "user" | "instructor" | "admin"` unions in the user admin components that #274 had not found by reading the code. The split that results is worth stating plainly: `vocabularies.ts` holds the legal values, `viewer.ts` holds the questions asked about them.

[ADR-0014](./0014-status-vocabularies-live-in-src-lib.md) put the status tuples in `src/lib` so that a client-safe module naming a status would not drag `drizzle-orm` into the bundle. That argument does not carry a role anywhere, because `user.role` is `text` owned by Better Auth's admin plugin and there is no `pgEnum` to derive from in the first place. What follows from the missing column constraint is that the tuple is the only anchor a role has: a status the app misspells is a row Postgres rejects, and a role the app misspells is a row it accepts and nothing selects. So the scan is not a second line of defence here the way it is for statuses. It is the only one.

## Consequences

`STAFF_ROLES` is held to the vocabulary by `as const satisfies readonly UserRole[]` rather than derived from it, because which roles carry staff powers is a judgement and a fourth role must not become staff by arriving. The same `satisfies` appears on the two role names in `admin()` in `src/lib/auth.ts`, written on the literals rather than passed as the tuple: the plugin types `defaultRole` as `string` and `adminRoles` as `string | string[]`, so a readonly tuple is not assignable, and handing it the whole vocabulary would make every role an admin. Both spellings buy the same thing, which is that a role renamed in the tuple fails to compile rather than quietly stripping powers.

There is one order and no reader's order beside it. `PROJECT_STATUSES_IN_DISPLAY_ORDER` exists because `pgEnum` pins the status tuple's order in the database and reordering it is a migration; nothing pins this tuple, so the admin filter, the two role selects and the analytics breakdown all read it directly. The visible effect is that the analytics chart lists `user, instructor, admin` where it listed `admin, instructor, user` before.

The `makeUser` helpers in the integration suites still write the union out by hand, a dozen times. The scan skips `__tests__` on purpose, and its docblock says why: it cannot tell a test's case list from its expected value. Those copies are stale-able and were left alone rather than swept, because a test that names the roles it seeds is naming its own fixture, not restating the vocabulary.
