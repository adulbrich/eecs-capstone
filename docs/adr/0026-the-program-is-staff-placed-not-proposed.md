# The program is staff placed, not proposed

A project's program is set by staff from the staff panel and by nobody else. The picker left `project-form.tsx`, `program_id` left `ProjectInput`, and `updateProjectProgramAs` is the only writer after create, which writes a null. This applies [ADR-0007](./0007-proposer-linking-by-email.md)'s division consistently: #322 moved the proposer and the categories off the shared form because they are staff judgements about a submission rather than facts the submitter reports, and left the program behind, where its help text told the proposer "Staff can set or change it during review" while the control sat in front of them. Which course a project runs in depends on how many teams a term can carry, which programs are short of work, and what else is already placed, none of which a proposer can see. The cost is real and was accepted: a proposer often does know the course they are aiming at, and now has to say so in the description or a private note instead of picking it, and a staff-created project no longer arrives placed. The alternative, a second writer in the panel with the form's picker left in place, was rejected because one value with two writers in two places is how the proposer and staff come to disagree about it, and nobody is told (#109). Decided 2026-09-17 in #450.

## Consequences

`ProjectInput` has no `programId`, so `createProjectAs` always writes a null and `updateProjectAs` cannot touch the column; a fixture that wants a placed project creates it and then calls the staff writer, which is the order the panel works in. The Program section sits between Status and Proposer in the staff panel, reads its starting value from the detail payload rather than loading its own, and writes one `project_edit_log` row per change under the field name `programId`. The writer refreshes no embedding, for the reason the proposer and mentor writers skip one: the column is not part of the embedded text, since the program left `buildProjectEmbeddingSource` in #463 ([ADR-0025](./0025-the-embedded-text-is-prose-only.md)). The writer does not touch the scope assessment either, whose source hash already covers the program's `term_count` and which reports itself stale on read. Notifying the proposer that staff moved their project is #109's, not this one's. Superseded in part by [ADR-0028](./0028-a-project-runs-in-many-programs.md), which makes the program a set: the staff-placed division above survives untouched and only the cardinality changed, so the field name in the edit log is now `programs` and `createProjectAs` writes no join rows rather than a null column.

Extended in #491 to the openings flag, on the same reasoning rather than as a new decision. `projects.accepting_applicants` says whether a team still has room, and `CONTEXT.md` records under **Team is full** that the app never learns who would join because bidding and assignment happen outside it. Staff run that process, so staff are the party who find out a team filled up and the proposer usually hears it from them, which is the same asymmetry the program has. So the checkbox left `project-form.tsx`, `acceptingApplicants` left `ProjectInput`, and the section, renamed **Programs and teams**, carries it. It rides `updateProjectProgramsAs` rather than getting a writer of its own, because three Save buttons in one section would be worse than the navigation the change removes; the endpoint checks the program set and the flag separately, so a change to either alone saves, and logs a row per changed field so `acceptingApplicants` keeps the name it had when the form wrote it. `teams_supported` is deliberately not covered: how many teams a proposer can host is capacity they state about themselves and staff have no way to know it, which is the opposite asymmetry. #468 takes that field up separately and records its own ADR for it.
