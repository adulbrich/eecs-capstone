# A project runs in many programs

A project runs in a set of programs, held in `project_programs`, rather than in the one `projects.program_id` named. The set is unordered and displayed in `course_id` order; zero, one and many are all ordinary. This exists because a CS46X section offered both in Corvallis and on Ecampus is one proposal, one sponsor and one team roster filed under two courses, and the single column forced staff to pick one, after which the other program's students never saw the project in their filtered listing and the project page showed one badge where two were true. `teams_supported` stays a single integer on `projects`, shared across a project's programs rather than counted per program: per-program counts are the better model and are a second breaking change that would also take a field away from the proposer form, so they are #469 and not this. The cost is accepted and visible: a shared project contributes its whole `teams_supported` to each program's analytics slot count, so per-program figures no longer sum to the global one, and the staff panel warns when a project runs in more programs than it supports teams rather than refusing the save. The alternative, a nullable "primary program" beside the set, was rejected because it reintroduces the single value this replaces and gives every renderer a second question to answer. Decided 2026-09-17 in #462.

## Consequences

`projects.program_id` and `projects_program_id_idx` are gone, and the migration that drops the column carries a hand-written backfill insert ahead of the drop, because `drizzle-kit generate` emits the `CREATE TABLE` and the `DROP COLUMN` with nothing between them. The join row is `on delete cascade` on both sides, replacing `on delete set null`: deleting a program leaves a single-program project unplaced, exactly as before, and removes only that program from a shared one. Every read that renders the set goes through `projectProgramsList` or `projectProgramsText` in `project-summary.ts` (the analytics breakdown, the scope-assessment loader and the two program counters query the join table directly, because none of them renders the list), correlated subqueries rather than joins so a project row is never multiplied by its program count, and every filter goes through `runsInProgram` or `inNoProgram`, so `?program=X` is an any-match and the filter itself stays single-valued. `updateProjectProgramsAs` is still the app's only writer and still staff only (the legacy importer and the seed insert rows too, as they always did for the column) ([ADR-0026](./0026-the-program-is-staff-placed-not-proposed.md) is untouched by this); it compares the incoming set as a set, so a reorder writes nothing, and hand rolls its `project_edit_log` row under the field name `programs`, because there is no column left for `diffRowFields` to read. The staff control is a checkbox list, which retires the `_none_` sentinel the single picker needed: unchecking everything is the cleared set. `buildScopeSource` takes a list and its zero and single program output is byte identical to what it was, pinned by a test, so no stored scope verdict goes stale on this change; the system prompt's "the program the proposal is filed under" did have to change, and that one edit has no staleness signal behind it because `scopeSourceHash` covers the source and the model id, not the prompt.
