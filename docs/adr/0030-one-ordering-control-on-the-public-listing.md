# The public listing has one ordering control, and its table headers do not sort

`/projects` orders its rows in one place, the Sort select, which is a server ordering carried in `?order=` and applied identically in card and table view. Every column in `PROJECT_TABLE_COLUMNS` is `enableSorting: false` and the route's search schema carries no `sort` or `dir`, so a column header is a label rather than a button. The select grew to cover what the headers did: Newest, Oldest, Title A-Z and Recently updated beside the existing Recommended for you and Most relevant. Page-local sorting was deliberate before this, on the reasoning that the server's `order` picks which twenty rows are on the page and the column sort arranges them on it, and it did not survive contact: page two sorted independently of page one, so a reader sorting by Title walked an alphabet that restarted every page, and `PROJECT_TABLE_DEFAULT_SORT` of `updatedAt desc` was applied before any click, which is how choosing "Recommended for you" and switching to table view produced recommendation-selected rows in Updated order. The same change collapses a duplicate: with an empty search box `relevance` compiled to `coalesce(published_at, created_at) DESC`, byte for byte what `newest` compiles to, so the select read "Most relevant" over date-ordered rows, and `relevance` without a query now resolves to `newest` on the server. The cost is accepted: a reader who wants the table ordered by a column that is not one of the six options no longer can, and Contact name and Contact email are deliberately among those, because ordering a public catalog by a contact's surname is a staff shaped job. Decided 2026-09-17 in #475.

## Consequences

`searchProjectsImpl` resolves every ordering that cannot always be delivered, rather than the caller doing it: `recommended` needs an interest vector and `relevance` needs a query, and each degrades to what a viewer with no vector would get, which is `relevance` with a query typed and `newest` without. The resolved value comes back as `order` and the route renders that rather than the URL value, which is what #424 built it for, so the select and the rows cannot disagree and a URL carrying `?order=relevance` with an empty box reads Newest. "Most relevant" is absent from the option list while the box is empty rather than disabled, because with no query it is not a different ordering; it is gated on the committed `q` rather than the draft, or it would appear and vanish between keystrokes. Every ordering still ends in `projects.id` through the existing second argument to `.orderBy`, so paging stays total: see "Paging a listing needs a total ordering" in `docs/QUIRKS.md`. Title sorts on `lower(title)` so "Zebra" does not precede "apple", and needs no null handling because the column is `NOT NULL`. "Recently updated" is `updated_at DESC`, which the comment in `search.ts` argues against as the implicit listing date and not as a named choice a reader makes, and that distinction is worth keeping so the entry is not reverted. `CheckedAdminColumn` in `admin-data-table.tsx` now exempts `enableSorting: false` from the rule that a non-text accessor declares its own `sortFn`, which is what lets this table keep the accessors its cards and CSV read while sorting nothing. A stale link carrying `?sort=title&dir=asc` renders the listing normally, because Zod strips a key the schema does not know.
