# Each public listing has one ordering control, and its table headers do not sort

`/projects` orders its rows in one place, the Sort select, a server ordering in `?order=` applied identically in card and table view; every column is `enableSorting: false` and the search schema has no `sort` or `dir`. Header sorting arranged only the twenty rows on screen, so page two restarted the alphabet, and a default table sort overrode a chosen recommendation order. `searchProjectsImpl` resolves an ordering it cannot deliver (`recommended` with no interest vector, `relevance` with no query) and returns what it used, which the select renders. Every ordering ends in the row id, so paging stays total. The cost is that a column outside the options, contact name included, cannot order the table. `/inventory` followed in #477 with Available first, Name A-Z and Recently updated. Server-side column sort, the `/admin/users` pattern, was rejected because a header exists only in table view. Decided 2026-09-17 in #475.
