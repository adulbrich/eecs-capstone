# Each public listing has one ordering control, and its table headers do not sort

`/projects` orders its rows in one place, the Sort select, which is a server ordering carried in `?order=` and applied identically in card and table view. Every column in `PROJECT_TABLE_COLUMNS` is `enableSorting: false` and the route's search schema carries no `sort` or `dir`, so a column header is a label rather than a button. The select grew to cover what the headers did: Newest, Oldest, Title A-Z and Recently updated beside the existing Recommended for you and Most relevant. Page-local sorting was deliberate before this, on the reasoning that the server's `order` picks which twenty rows are on the page and the column sort arranges them on it, and it did not survive contact: page two sorted independently of page one, so a reader sorting by Title walked an alphabet that restarted every page, and `PROJECT_TABLE_DEFAULT_SORT` of `updatedAt desc` was applied before any click, which is how choosing "Recommended for you" and switching to table view produced recommendation-selected rows in Updated order. The same change collapses a duplicate: with an empty search box `relevance` compiled to `coalesce(published_at, created_at) DESC`, byte for byte what `newest` compiles to, so the select read "Most relevant" over date-ordered rows, and `relevance` without a query now resolves to `newest` on the server. The cost is accepted: a reader who wants the table ordered by a column that is not one of the six options no longer can, and Contact name and Contact email are deliberately among those, because ordering a public catalog by a contact's surname is a staff shaped job. Decided 2026-09-17 in #475. `/inventory` followed on 2026-09-22 in #477, for the same two defects: its headers sorted only the twenty rows on screen, and `listInventory` paged on `updated_at DESC` alone, which is not a total ordering. Its select offers Available first, Name A-Z and Recently updated, and defaults to Available first, because someone browsing the catalog wants what they can take out now; Recently updated, the ordering card view showed until then, stays as a named choice. Server-side column sort, the `/admin/users` pattern, was the alternative and lost on card view: a header exists only in the table, so `?sort=` in the loader would have ordered the cards by a control no one could see.

## Consequences

`searchProjectsImpl` resolves every ordering that cannot always be delivered, rather than the caller doing it: `recommended` needs an interest vector and `relevance` needs a query, and each degrades to what a viewer with no vector would get, which is `relevance` with a query typed and `newest` without. The resolved value comes back as `order` and the route renders that rather than the URL value, which is what #424 built it for, so the select and the rows cannot disagree and a URL carrying `?order=relevance` with an empty box reads Newest. "Most relevant" is absent from the option list while the box is empty rather than disabled, because with no query it is not a different ordering; it is gated on the committed `q` rather than the draft, or it would appear and vanish between keystrokes. Every ordering still ends in `projects.id` through the existing second argument to `.orderBy`, so paging stays total: see "Paging a listing needs a total ordering" in `docs/QUIRKS.md`. Title sorts on `lower(title)` so "Zebra" does not precede "apple", and needs no null handling because the column is `NOT NULL`. "Recently updated" is `updated_at DESC`, which the comment in `search.ts` argues against as the implicit listing date and not as a named choice a reader makes, and that distinction is worth keeping so the entry is not reverted. `CheckedAdminColumn` in `admin-data-table.tsx` now exempts `enableSorting: false` from the rule that a non-text accessor declares its own `sortFn`, which is what lets this table keep the accessors its cards and CSV read while sorting nothing. A stale link carrying `?sort=title&dir=asc` renders the listing normally, because Zod strips a key the schema does not know.

On `/inventory` nothing needs resolving, because all three orderings can always be delivered: `order` is optional in the route so the URL stays bare until a reader picks, and `listInventorySchema` defaults it. The orderings are a `Record` keyed by the union in `inventory-catalog.ts`, each followed by `inventory_items.id`. Available first sorts on the `inventory_item_status` enum itself, whose declaration order is the lifecycle order `statusRank` reads, so it needs no CASE expression; then on `lower(name)`. The enum follows the migration rather than `INVENTORY_ITEM_STATUSES`, and an integration test pins the two together. Search still filters without ranking: a relevance ordering while a query is typed, the way `/projects` has one, was considered and left out, since the catalog is small enough that a query rarely returns more than a handful of items.
