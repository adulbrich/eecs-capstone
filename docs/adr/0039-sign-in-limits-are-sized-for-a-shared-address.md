# Sign-in limits are sized for a shared address, and brute force moves elsewhere

Amended on 2026-09-22 by [#576](https://github.com/adulbrich/eecs-capstone/issues/576): password sign-in is gone. `/sign-in/email`, `/sign-up/email` and `/change-password` are 404 through `disabledPaths` and carry no rule, and the per-account attempt counter (#552), its `sign_in_attempts` table and the failure count DEPLOYMENT.md used to query were deleted with them. What stands is the argument about a shared address, which is what sizes the paths that are left, the code-entry ones included ([ADR-0047](./0047-sign-in-by-emailed-code-rather-than-magic-link.md)). Everything below about a password describes a path that no longer exists.

Better Auth's rate limiter keys every bucket on the resolved viewer address and the path, and `createRateLimitKey(ip, path)` takes no configuration, so a rule can change how much an address may spend but never what an address means. OSU wireless NATs students into a pool of shared public addresses, which makes one bucket cover however many devices sit behind one pool address, so every number Better Auth ships is being asked a question it was not sized for. Its first special rule, 3 per 10 seconds, matches `/sign-in`, `/sign-up`, `/change-password` and `/change-email` as prefixes and reaches six mounted paths here. Three of them check no credential at all: `/sign-in/oauth2` and `/sign-in/social` mint an OAuth state and redirect, so the password is typed at Microsoft or GitHub who run their own defences, and `/sign-up/email` creates an account. Behind a pool address, 3 on those three is not brute force protection, it is a refusal for the fourth student since the last lull on the paths a new student reaches first, caused by nobody's behaviour and impossible to reproduce. So those three go to 60. `/change-password` goes to 5, because the legitimate call rate is near zero and because `update-user.mjs` hashes the new password before verifying the current one, so a wrong guess costs a full scrypt hash plus a full scrypt verify, about 118 ms of CPU, on a fleet of three to four tasks with no WAF in front. The CPU and the budget do not have the same reach: `sensitiveSessionMiddleware` rejects an unauthenticated call before any hashing, so only a signed-in attacker spends CPU, but the limiter runs in the router's `onRequest` ahead of middleware, so five anonymous 401s from one pool address refuse `/change-password` for everyone behind it until a lull. That griefing is accepted over the CPU, because changing a password is rare and the refusal clears itself. `/get-session` stops being limited at all, because `authClient.useSession()` calls it on every page render, 136 of the 139 `/api/auth/*` requests measured in #535, and it reads a session the caller already holds a cookie for. `/sign-in/email` keeps the default, and that is the decision this ADR exists for: raising it would be consistent with everything above and is wrong, because `emailVerification.sendOnSignIn` mails a fresh verification link on every successful sign-in to an unverified account, and sign-up is open, so anyone can register an address they do not own with a password of their choosing. That number is therefore also what throttles verification mail aimed at a stranger's inbox, and 60 would make it twenty times easier (#554). `/change-email` keeps the default too, for the weaker reason that no flow calls it, though it is mounted and a direct call is served and counted. Both OAuth paths keep a limit rather than being switched off because each writes an OAuth state row per call, and `/sign-in/oauth2` additionally refetches the ONID discovery document from Microsoft, uncached (#553). The consequence worth stating plainly is that per-address limiting cannot protect a credential behind NAT at any number, so the control moves to a per-account attempt counter keyed on the account and the address together (#552). Decided 2026-09-21 in #535.

## Consequences

Read every number here as a budget between lulls rather than a rate. Better Auth clears a count only after a gap longer than the window with no accepted request, and every accepted request pushes that gap out, so a trickle far under the nominal rate still accumulates to the max and is then refused until the address falls quiet; `src/lib/__tests__/auth-rate-limits.test.ts` pins that behaviour. So 60 does not make a refusal impossible at term start, it makes it roughly twenty times rarer and self-clearing, which is the whole of what a per-address number can buy here. Campus pays for the `/sign-in/email` decision in the same currency: password sign-in keeps a limit this ADR argues is the wrong shape everywhere else, accepted because ONID is what students use and the password population is a few dozen staff and mentors, and because the alternative was shipping a mail amplifier. Three changes are now in flight and the ordering matters: the second half of #535 sets the ALB to `preserve` (shipped in #556), removing the roughly five-to-one CloudFront edge dilution measured in #535, and until that is applied every number here is spread across edge addresses and multiplied again by the running task count, two to four under #529, because the counter is per task and in memory. That product is why `/sign-in/email` at 3 throttles rather than bounds: fleet-wide it is a multiple of 3, not 3. The limits deploy before the load balancer changes, because correcting the key first would remove the dilution that is currently the only thing keeping the old numbers from biting. `storage: "database"` was considered and rejected on scope rather than on principle: the cost is negligible once `/get-session` is exempt, and the case for it is real, because `/change-password` is now the one number left here that still guards a credential and the per-task multiplier applies to it too. It belongs with #552, which is where a shared counter has to exist anyway, rather than bolted onto a PR whose job is the numbers. `/sign-up/email` at 60 is the raise with the largest blast radius and it is not only an SES quota question: bounces to addresses that do not exist cost sender reputation, a suspended SES identity would take password reset down with verification, and, as `src/lib/auth.ts` already documents on `accountLinking`, an unverified password account holding a student's address makes that student's first ONID sign-in fail with `account not linked`, so squatting a roster turns a student's first ONID sign-in into a failure at exactly the term start this work is sized for. Not a permanent denial: the student can recover through forgot-password, then a password sign-in, then the verification mail that sign-in triggers, after which ONID links. That is a maze most people would report as broken rather than solve. It was possible before at 18 addresses a minute and is possible now at 360; #554 carries the fix. Note for anyone checking the arithmetic: #535's body quotes Better Auth's global default as 100 per 60 seconds, which is what the upstream prose docs say and is wrong for the pinned version, where it is 100 per 10 seconds. The rejected alternatives for protecting `/sign-in/email` were Cloudflare Turnstile and AWS WAF account takeover prevention; both work, and both were declined in favour of #552 because they add a vendor, and because a captcha fails closed on a missing token, so it would break every browser test that signs in through the password form unless gated to production, which means shipping a control CI never runs.

Two things this ADR handed to #552 came back different, and the record moves with them rather than leaving the reader to find a merged PR. The refusal is not the byte-identical `INVALID_EMAIL_OR_PASSWORD` the issue specified: it is a `TOO_MANY_REQUESTS` naming a duration, thrown before the password is checked, so it differs in status, code, message and timing alike. Byte-identical was the right instinct and the wrong call here, because the enumeration it protects against is already closed by the counter counting addresses with no account, which makes a refusal a statement about how often this caller has tried and not about whether the account exists, while a fourth identical "invalid email or password" tells a person whose password is correct to go and change it rather than wait sixty seconds. The condition attached to that is load-bearing: if anyone ever makes the counter skip addresses with no account, the message has to become the generic one in the same commit, and `tooManyAttemptsMessage` says so where it is defined. `storage: "database"` did not ship with #552 either, and the reason is arithmetic rather than scope: turning it on divides every number above by the running task count, three to four, in the same week #556 removed the roughly five-to-one CloudFront dilution those numbers were sized against, and two multipliers leaving at once a fortnight before a term start is how a limit becomes a lockout. It moves to #560 with its own measurement. What did ship alongside it is the fleet-wide failure count #552 asked for, which this ADR did not: one log line per recorded failure, carrying no address and no email. Be precise about what that buys, because the issue's own framing is generous. A count with no identifiers in it is an alarm and not a diagnosis: it cannot separate a spray across ten thousand accounts from ten thousand addresses attacking one account, and it cannot separate either from a first week of term where everyone mistypes a password. What it can do is make any of them visible at all, which no per-pair counter can, and the shape is then a query against `sign_in_attempts`, which holds the identifiers the log line deliberately does not. Both queries are in DEPLOYMENT.md.
