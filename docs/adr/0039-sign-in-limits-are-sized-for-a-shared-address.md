# Sign-in limits are sized for a shared address, and brute force moves elsewhere

Better Auth's rate limiter keys every bucket on the resolved viewer address and the path, and `createRateLimitKey(ip, path)` takes no configuration, so a rule can change how much an address may spend but never what an address means. OSU wireless NATs students into a pool of shared public addresses, which makes one bucket cover however many devices sit behind one pool address, so every number Better Auth ships is being asked a question it was not sized for. Its first special rule, 3 per 10 seconds, matches `/sign-in`, `/sign-up`, `/change-password` and `/change-email` as prefixes, and reaches five paths in this app. Three of them check no credential at all: `/sign-in/oauth2` and `/sign-in/social` mint an OAuth state and redirect, so the password is typed at Microsoft or GitHub who run their own defences, and `/sign-up/email` creates an account. Behind a pool address, 3 per 10 seconds on those three is not brute force protection, it is a lockout for the fourth student in ten seconds on the paths a new student reaches first, caused by nobody's behaviour and impossible to reproduce. So those three go to 60, which is past a lecture hall clicking at once and short of a script. `/change-password` goes to 20, and the reason is the legitimate call rate rather than the credential check: nobody changes their own password twenty times in ten seconds, so a smaller number costs a real user nothing and still bounds whoever holds a stolen session. `/get-session` stops being limited at all, because `authClient.useSession()` calls it on every page render, 136 of the 139 `/api/auth/*` requests measured in #535, and it reads a session the caller already holds a cookie for. The fifth path, `/sign-in/email`, keeps the default, and that is the decision this ADR exists for: raising it would be consistent with everything above and is wrong, because `emailVerification.sendOnSignIn` mails a fresh verification link on every successful sign-in to an unverified account, and sign-up is open, so anyone can register an address they do not own with a password of their choosing. The route limit is therefore also the ceiling on verification mail aimed at a stranger's inbox, and 60 would make that twenty times easier (#554). Both OAuth paths keep a limit rather than being switched off because each writes an OAuth state row per call, and `/sign-in/oauth2` additionally refetches the ONID discovery document from Microsoft, uncached, twice per sign-in (#553). The consequence worth stating plainly is that per-address limiting cannot protect a credential behind NAT at any number, so the control moves to a per-account attempt counter keyed on the account and the address together (#552). Decided 2026-09-21 in #535.

## Consequences

Campus pays for the `/sign-in/email` decision: password sign-in keeps a limit this ADR argues is the wrong shape everywhere else, and behind a shared pool address the fourth staff member or mentor in ten seconds is refused. That is accepted because ONID is what students use and the password population is a few dozen people, not a lecture hall, and because the alternative was shipping a mail bomb. #554 removes the bind by metering the send instead of the route, and #552 should then carry the raise. Ordering matters and there are now three changes in flight: the second half of #535 sets the ALB to `preserve`, which removes the roughly five-to-one CloudFront edge dilution measured in #535, and until it lands every number here is diluted across edge addresses and multiplied again by the running task count, two to four under #529, because the counter is per task and in memory. That compounding loosens rather than tightens, so it is a known overshoot rather than a hole, and it is also why the limits deploy before the load balancer changes: correcting the key first would remove the dilution that is currently the only thing keeping the old numbers from biting. `storage: "database"` was considered and rejected, not on cost, which is negligible once `/get-session` is exempt and the limited paths are three requests in 139, but because nothing left under this limiter is a security control, so paying for an exact count buys precision in a number that is deliberately approximate. Note for anyone checking the arithmetic: #535's body quotes Better Auth's global default as 100 per 60 seconds, which is what the upstream prose docs say and is wrong for the pinned version, where it is 100 per 10 seconds. `/sign-up/email` at 60 allows 360 distinct addresses a minute to be mailed once each, which is SES quota and sender reputation rather than a victim, since Better Auth sends nothing on a repeat sign-up for an address that already exists. The rejected alternatives for protecting `/sign-in/email` were Cloudflare Turnstile and AWS WAF account takeover prevention; both work, and both were declined in favour of #552 because they add a vendor, and because a captcha fails closed on a missing token, so it would break every browser test that signs in through the password form unless gated to production, which means shipping a control CI never runs.
