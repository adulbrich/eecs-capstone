# Scale the service, and let the task count pick the database instance

The app service gains Application Auto Scaling between two and four tasks, target tracking average CPU at 50%; `container_memory` goes from 512 MB to 1024; the deployment circuit breaker is turned on with rollback; and `db_instance_class` moves from `db.t4g.micro` to `db.t4g.small`. The first three are what #522 measured for a 500 student term start: memory peaked at 44.7% of 512 MB with almost no concurrent users while CPU peaked at 23.9%, so memory is the binding resource and SSR concurrency is what 500 students add; a floor of two rather than one is because ECS takes 60 to 90 seconds to replace a crashed task and with one task nothing serves in the meantime, which is worth $8.51 a month in the term the site is actually used. The fourth is not a capacity decision but a consequence of the other three, and it is the reason this is an ADR rather than a diff: [ADR-0034](./0034-the-pool-is-sized-against-the-instance.md) sized the connection pool against the instance a week earlier and said in as many words that scaling past its task ceiling means a bigger instance or a smaller pool. A deploy runs old and new tasks side by side at `maximumPercent` 200, so a ceiling of four is a worst case of eight tasks wanting 200 connections, 210 counting the one-off script reservation, and `db.t4g.micro` has 107 usable. The instance moved rather than the pool because halving the pool to fit would undo #521 in the same month it shipped, and because #522 measured RDS CPU at 6.6% with credits flat, so the instance was never sized by load in the first place. Scaling on CPU rather than memory despite memory being the binding resource: a Node process grows its heap to fill what it is given and returns it slowly, so `MemoryUtilization` ratchets up and never falls, which adds tasks and never removes them. The memory answer is the raise to 1024, not a scaling signal. Decided 2026-09-20 in #522, with the instance class and the task floor confirmed by the maintainer against their costs.

## Consequences

Recurring cost goes up by about $21.49 a month at the floor: $11.68 for the instance, $8.51 for the second always-on task, $1.30 for the extra memory on the first. Tasks three and four cost $8.51 a month each only for the hours they run. `CONNECTION_BUDGET` in `src/lib/_internal/db-pool.ts` now reads 220 usable and a ceiling of eight, and its unit test is what stops the next raise from overrunning the instance silently: it reads `app_max_tasks` out of `infra/variables.tf` and fails when the two writings of the task count disagree, so the doubling rule is checked rather than remembered. The deploy workflow stopped passing `--desired-count 1`, which it had done since before there was a scaler; leaving it would have set the fleet back to one task on every deploy and kept it there until a scaling alarm fired, which is the outage window the floor was bought to remove. The instance class change restarts the database: `apply_immediately` is true and `multi_az` is false, so `terraform apply` takes the site down for a few minutes rather than waiting for a maintenance window, and it should be applied when nobody is mid-submission. None of this is proven under load; #524 is the load test, and these numbers are extrapolation from a workload of a few admin users. The scaling signal is worth revisiting once #524 has run, because if memory turns out to lead CPU under real concurrency then the CPU policy will not fire when it matters and the answer is a larger task rather than a memory policy.
