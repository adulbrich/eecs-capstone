# The embedding source limit is a character cap standing in for a token ceiling

`EMBEDDING_SOURCE_LIMIT` truncates the embedded text at 20,000 characters, chosen on 2026-09-20 to keep the embed call under Titan Text Embeddings V2's ceiling of 8,192 tokens. The two units do not convert, and that is the whole difficulty: no character count can guarantee a token count. The limit was 45,000 until this decision for exactly that reason, taken from the model's 50,000-character figure, which never binds because the token ceiling is reached first. Nothing had hit it, because every project in the corpus was under 9,000 characters of source; the legacy import is what broke that, with three rows from one sponsor at 34,000 to 36,000 characters of pasted links, refused at 9,999, 9,202 and 13,103 tokens when measured against Bedrock. 20,000 is the project form's own cap total, 20,200 characters plus labels and joins, made explicit, and at the worst density the corpus contains, 2.63 characters per token on the densest of those rows, it lands near 7,600 tokens. The alternative, catching the rejection inside `bedrockEmbed` and retrying on a shorter input, was rejected: it embeds a truncated string while `embeddingHash` covers the full one, so the stored vector stops matching what its hash says it is and a later change to the retry ratio invalidates nothing. Truncating in the source builder keeps the hash over exactly what was embedded, which is the property the hash exists for.

## Consequences

Changing this number re-embeds every row whose source is longer than it, at one paid Bedrock call each, because the truncated string is what the hash covers. This change costs nothing, since the form's caps bound an existing row at about 20,300 characters and the longest source in the imported archived cohort is 8,722, so no stored hash moves. Text denser than 2.63 characters per token can still overflow 20,000 characters, and this deliberately does not solve that: such a row behaves exactly as an oversized row does today, `refreshProjectEmbedding` returns `"failed"`, the vector stays null, the row sorts last under `recommended` (#427), and every later sweep retries it at one wasted call. `src/lib/__tests__/embedding-source.test.ts` pins the arithmetic the number was chosen by rather than the number itself, so the density assumption is visible instead of folded into a literal; it is a floor on the reasoning, not on the limit, and it admits any value under about 21,560. What fails on a change to the number itself is the literal in `src/test/backfill-embeddings-parity.test.ts`, which pins it across the three places it lives: the lib, the `.mjs` the production image ships (ADR-0024), and the test's own copy.
