# The pool keeps a warm floor of five connections

In production the app pool holds `POOL_MIN`, five connections per task, open through any lull, and opens them on the task's first request, which is the load balancer's health check. `src/lib/_internal/db-pool.ts` carries the number and `warmPool`; `src/db/index.ts` turns both on under the same production gate as the pool metric, and `src/server.ts` imports `#/db` so the warm-up runs before a new task takes traffic. The 2026-09-23 load test drew one 500 twice, from a task that had just scaled out and then from one 41 to 64 minutes old, and what the two share is not age but a pool with nothing open meeting a 42 requests per second burst (#601): pg-pool closes a client idle for 10 s, so after any lull a task opens every connection while its 0.25 vCPU is saturated serving the burst, and both failures took just over the 5 s `connectionTimeoutMillis` that pg-pool applies to a connect as well as a queue wait, with `PoolWaiting` at 0. `min` alone would have fixed only the second case, because pg-pool opens nothing to reach it; a warm-up alone would have fixed only the first, because the idle timeout closes what it opened ten seconds later. The floor sits inside `POOL_MAX`, so [ADR-0034](./0034-the-pool-is-sized-against-the-instance.md)'s ceiling and its test are unchanged; what moves is the resting count, `(5 + 5) * 4 = 40` of 220 with the traffic writer's floor-less reservation counted at its cap. The alternatives in #601 stand behind this rather than beside it: the target group's `slow_start` helps only a new task and not a warm one after a lull, and giving a connect longer than a queue wait needs a timeout pg-pool does not separate. Five is the issue's number, not a measured one; the busiest pool reached 22 to 31 in those bursts, so five is a head start on the connects a burst needs rather than all of them. Decided 2026-09-23.

## Consequences

This is a hypothesis until a lull-then-burst run confirms it, and that run is the follow-up: repeat the three-task burst after at least ten idle minutes, and phase 1c then the burst without letting the scaled-out task warm, and record both under `docs/load-tests/`. If a 500 still lands, the floor goes up before the timeout does, and the log line from #602 now names the route and the cause. Dev, the test suites and the scripts keep no floor, because a client under `min` is never closed and a module evaluated twice (dev HMR, a test worker) would hold a stale pool's five open for good; `allowExitOnIdle` goes with the floor so that a script run with `NODE_ENV=production` can still exit. A task that cannot reach the database at boot still comes up: `warmPool` logs one redacted line and the pool opens connections on demand as before. The floor is not self-healing: a connection that drops (an RDS failover or reboot) is removed and not reopened, and the floor refills only as demand opens connections again, so the first burst after a drop can start below five. Reopening proactively would need a timer beside pg-pool, which is more machinery than a failover every few months earns. The hourly `DatabaseConnections` minimum is the signal that the floor is held: about five per task plus whatever the traffic writer has open, lower only in the hour after a drop.
