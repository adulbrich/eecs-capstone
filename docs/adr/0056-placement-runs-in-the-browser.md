# Placement runs in the browser

Staff place students on projects with a tool at `/admin/placement` that parses the bids file, solves the placement and keeps the whole workspace in the staff member's own browser, and no bid, comment or placement ever reaches the server. The data is the reason: a bid carries a student's name, email, the reason they want a project and, in the same survey, the name of a classmate they would rather not work with, all of which are education records under FERPA, and the app today holds nothing of the kind. Keeping them off the server means no table to secure, retain, back up, anonymize on account deletion ([ADR-0008](./0008-account-deletion-anonymizes.md)) or leak through a log, and no student needs an account for placement to work. The alternative was #33's design, students bidding in the app into `project_bids` and staff assigning into `project_assignments`; it closed unbuilt because programs run bidding differently, and its tables leave with #646. What this costs is sharing: two staff members cannot work one placement at once, the workspace moves between machines only as an exported file, and it lasts only as long as that browser's storage. The one server call the tool makes is the staff read of a program's published projects: the request sends nothing but the program, and the response holds project fields staff already see in the projects table. The solver is HiGHS compiled to WebAssembly and run in a Web Worker, which is what makes the rest possible: the model the R script solved with GLPK is small enough to solve in a tab. Decided 2026-09-25 in #644.
