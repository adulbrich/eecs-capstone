# Rejected legacy proposals import as `changes_requested`

The old portal's `Rejected` (`cp_cps_id = 3`) has no counterpart in this app, and DEPLOYMENT.md said so: `changes_requested` means "resubmit" and the portal's Rejected is terminal, so 49 rejected rows were deferred with the drafts. That reasoning holds only while nobody intends to work on the rows, and on 2026-09-20 staff asked for a cohort they do intend to rewrite here, which makes "terminal" the wrong description of them. `changes_requested` is what this vocabulary has for a proposal staff turned down that its proposer may still fix, so the importer now writes it. The alternative considered was `draft`, which would have cost the same one-line change to `IMPORTABLE_STATUSES`, but it says the project was never submitted, which is false of every one of these and erases the only thing the legacy status recorded. Importing them exposes nothing: `search.ts` serves `published` and `archived` only, so neither this status nor `approved` reaches a public path. Staff can edit them from the moment they land, because `canEditProject` grants staff every project that is not soft-deleted. The proposer cannot, yet: `resolveProposers` binds `proposer_id` by matching `user` rows on email, and a legacy proposer who has never signed up here has no such row, so these land with no owner and `OwnerProjectActions` never mounts. Verification is not what gates it; existence of the account is. Staff rewriting them is the expected path either way, and `TRANSITIONS` gives `changes_requested` an onward move to `submitted` and `approved` when someone is ready. This narrows ADR-0031, which closes by saying what stays in the old portal is "drafts, rejections and archived submissions nobody ruled on": rejections are no longer categorically among them. Decided 2026-09-20, with no issue behind it; the rejected rows nobody plans to touch stay in the portal, where Rejected still is terminal.

## Consequences

Two asymmetries follow from writing a status the workflow normally reaches through `commitTransition`. Staff moving a project to `changes_requested` in the UI must say what to change, which `assertChangesRequestedHasComment` enforces, and this importer writes no status history for any status it writes, so an imported row carries no such comment and `owner-project-actions.tsx` renders "No note was left" in its place. That fallback already existed and is correct; the reason goes in `notes`, which staff and the proposer can both read and which `buildNotes` carries through. Writing status history from the importer was rejected rather than overlooked, because ADR-0004 gives that table exactly one writer and a second one would make the history disagree with itself. The other asymmetry is the one that decides whether this is worth doing at all: `projectInputSchema` caps `description` at 5,000 characters and the importer writes raw SQL, so a longer row imports cleanly and then cannot be saved from the editor, which defeats the only reason to bring it across. Rewriting the text to fit is part of importing this cohort, not tidying afterwards, and DEPLOYMENT.md 7a.8 says so. These rows are not in `EMBEDDABLE_STATUSES`, so they cost no Bedrock call and the 7a.5 backfill has nothing to do for them.
