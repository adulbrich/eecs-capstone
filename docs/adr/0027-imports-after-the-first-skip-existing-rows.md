# Every legacy import after a cohort's first one skips the rows it already has

`scripts/import-legacy.mjs` runs bare exactly once per cohort, for the import that creates it, and with `--skip-existing` every time after. The bare form is a full upsert: on a row it already imported it rewrites the 24 of the table's 32 columns its `ON CONFLICT` names, which is the project's own text, its flags, its dates, its proposer and its program, and it says nothing about what it replaced beyond a count of the rows it is about to overwrite. What escapes it is what makes it recoverable rather than catastrophic: `student_proposed`, `mentor_email`, `deleted_at`, the three embedding columns and the two `scope_assessment` ones are not in the upsert at all, and `image_url` is named but COALESCEd, so a mentor, a soft delete, a vector, a scope assessment and an image all survive. What a proposer or a staff member typed about the project itself does not. The rule exists because the app is now where the corrections happen: four live rows carry the literal string `0` in a proposer name or email, they are being fixed here rather than in the old portal, and a routine top-up under the bare form would put the `0` back silently. There is deliberately no standing exception. A mapping found to be wrong for every row in a cohort, the way `export.sql` read a dead column and left half the catalog with no program, is still only fixable by a full upsert, but that is a call made once, against the staff edits it discards and with a dump taken first, not a permission granted in advance. Decided 2026-09-17.

## Consequences

`--skip-existing` skips whole rows rather than the columns staff touched, so an existing project picks up nothing from a later export: not a retitled project, not a description rewritten in the old portal, not an image uploaded there afterwards. New rows arrive and existing ones freeze, which makes a cohort's first import the only cheap chance to get a row right and moves everything after it into the app by hand. The importer's closing `Imported N projects` counts every row in the file rather than the rows the run wrote, because its check queries `WHERE id = ANY($1)` over all of them, so a top-up adding 12 rows to a 203-row file still prints `Imported 203`; the `12 new, 191 already imported (skipped)` line above it is the honest one. A full re-run also re-links proposers whose accounts have since been deleted, and a skipping run does not, so that repair now needs the app rather than the pipeline. DEPLOYMENT.md's 7a.7 carries the operational detail.
