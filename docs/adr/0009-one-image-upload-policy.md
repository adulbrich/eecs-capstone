# One image upload policy, one owner of each image column, and cleanup after the row

The MIME allowlist, the size cap and the guard live once, in client-safe `src/lib/image-upload-policy.ts`, because three copies had drifted. An upload stores the object and returns its key without writing a row; the caller passes the key to the ordinary update, which is the column's only writer, so an image change reaches the diff and the edit log. The old object is deleted after the row write lands, never inside the transaction, and only when its key is inside the row's own prefix, since the column is client-writable and an unscoped delete would let a caller destroy another row's image. Both create paths refuse a key, because the id in `<domain>/<id>/` does not exist until the insert. The guard checks the change, not the content, so legacy rows holding absolute URLs stay editable. Hard delete cleans up; soft delete keeps the image.
