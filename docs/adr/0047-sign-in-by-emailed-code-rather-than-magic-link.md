# Sign-in is proved by an emailed code, not a magic link

Sign-in by address uses Better Auth's `emailOTP`, a six digit code typed back into the tab that asked, rather than `magicLink`: neither creates a `user` row before the address is proved, but a link opens in whatever browser the mail client picks, often a phone, and a forwarded link is a working session. Codes are stored `encrypted`, since an unsalted hash over a million codes reverses at once. A rotation resets a code's three guesses, so `SIGN_IN_CODE_LIMIT`, five sends an hour per recipient (ADR-0046), is the brute-force control. A redeem needs the claim from `src/lib/otp-claim.ts`, an HMAC cookie for the browser that asked; it gates the redeem, not the send, which would let a stranger who asks first lock the owner out. A stranger can still burn codes, denying code sign-in, but only by spending the owner's sends; one live code per browser would close that and was left out. `src/server/_internal/otp-sign-in-guard.ts` fails closed and refuses banned and provider-linked rows with `INVALID_OTP`, and `/email-otp/verify-email` is disabled, since it verifies without revoking a squatter's password. Sign-in without ONID or GitHub depends on mail. Decided 2026-09-22 in #576.
