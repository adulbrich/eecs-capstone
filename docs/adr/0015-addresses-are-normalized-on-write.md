# Email addresses are lowercased on write, in the four columns this app owns

`inventory_items.current_holder_email`, `inventory_item_status_history.holder_email`, `projects.proposer_email` and `projects.mentor_email` are trimmed and lowercased before they are stored, by `normalizeEmailAddress` in `src/lib/email-address.ts`. The alternative, kept until three read sites folded case at compare time (#196, #245, then the staff HolderField lookup), was to keep folding and say so. Folding does not use a plain btree index on the column, which is free at this table size and would not stay free, and each new comparison site was another place to remember the rule. Normalizing puts the rule in one function on the way in.

## Consequences

The stored address no longer preserves the case a person typed, which staff see in the Holder column and in history rows. `updateProjectMentorshipAs` writes the project edit log through `diffRowFields`, so the log records the normalized address, and an edit changing only case finds no changed field and reports `updated: false`. Both were argued the other way in that function's docblock before this, and are the price of the decision rather than defects to fix.

Reads still fold, and most of them always will. `user.email` is Better Auth's column, not one of these four, so `resolveHold`, `lookupUserByEmailAs` and `mentorNameSql` compare against it and keep their `lower()`. Better Auth happens to lowercase that column itself, both at each call site that creates an account and again inside `db/internal-adapter.mjs`, which makes those folds defensive rather than load-bearing; they stay, because that is a library's internals and an upgrade changing it would silently stop linking accounts. Only a `lower()` applied to one of the four columns above may be dropped, and only after `drizzle/0023_normalize_address_columns.sql` has run against a deployed database, which is why the write change and the read cleanup are separate releases.
