# The pool is sized against the instance, and traffic writes get their own

`src/lib/_internal/db-pool.ts` sets the app pool to 20 connections per task with a 5 second acquisition timeout, and carries the budget those numbers come from: 107 usable connections on `db.t4g.micro`, three app tasks at once, a one-off script's default pool of 10 beside them, and 5 per task reserved for the site traffic writer. Before this the pool was pg-pool's unset default of 10, and RDS `DatabaseConnections` sat at exactly 10 for a week under a handful of staff, which is no headroom at all before requests queue on the pool rather than on the database (#521). The number is chosen against the instance rather than the task, which is not where the issue pointed: an idle client measured at 0.11 MB of task RSS, so twenty are about 2 MB of 512, while the instance's freeable memory was 131 to 176 MB with ten backends open, so the raw `max_connections` arithmetic is not the limit and 20 is deliberately far under it. The timeout exists because `/api/healthz` never touches the database on purpose, so an exhausted pool with no timeout is every page hanging while the task stays green; failing fast is the failure that can be seen. The one carve-out from "one pool per process": the site traffic writer under #18 opens a second pool of its own, capped at the reserved 5, so a flood of anonymous writes fills its own queue and never a page render's. That pool is not built yet; the reservation is what this ADR holds. "Traffic writer" rather than "collector" because `CONTEXT.md` already uses collector for the person picking up an item. Decided 2026-09-20. Assumptions to revisit in #522: one task today, `db.t4g.micro`, 512 MB of task memory.

## Consequences

The unit test in `src/lib/__tests__/db-pool.test.ts` holds the sum (three tasks at 20 plus 5, plus the one-off 10) to the 107 ceiling, so raising the pool, the task ceiling or the traffic share has to keep the inequality true or change the instance. The one-off 10 is a reservation rather than a measurement: `deploy.yml` waits for the migration task to stop before it updates the service, and `migrate()` uses one session, but the other scripts under `scripts/` open pg's default pool and can run at any time. Autoscaling past three tasks means a bigger instance or a smaller pool, not a silent overrun. The honest post-deploy signal is the hourly `DatabaseConnections` maximum staying below 20; pg-pool closes clients idle for 10 seconds, so a quiet task holds fewer. If it pins to 20, headroom is gone again and the cause wants diagnosing before another raise. `docs/QUIRKS.md` "Pool reuse" points here for the traffic writer exception.
