# The pool is sized against the instance, and traffic writes get their own

`src/lib/_internal/db-pool.ts` sets the app pool to 20 connections per task with a 5 second acquisition timeout, and carries the budget those numbers come from: 220 usable connections on `db.t4g.small`, eight app tasks at once, a one-off script's default pool of 10 beside them, and 5 per task reserved for the site traffic writer. Before this the pool was pg-pool's unset default of 10, and RDS `DatabaseConnections` sat at exactly 10 for a week under a handful of staff, which is no headroom at all before requests queue on the pool rather than on the database (#521). The number is chosen against the instance rather than the task, which is not where the issue pointed: an idle client measured at 0.11 MB of task RSS, so twenty are about 2 MB of 1024, while the instance's connection ceiling is what the fleet total has to fit under. The timeout exists because `/api/healthz` never touches the database on purpose, so an exhausted pool with no timeout is every page hanging while the task stays green; failing fast is the failure that can be seen. The one carve-out from "one pool per process": the site traffic writer under #18 opens a second pool of its own, capped at the reserved 5, so a flood of anonymous writes fills its own queue and never a page render's. That pool is `src/db/traffic.ts`, built in #591, which drops an event rather than wait once the reserved 5 are in flight. "Traffic writer" rather than "collector" because `CONTEXT.md` already uses collector for the person picking up an item. Decided 2026-09-20. Revised the same day by [ADR-0035](./0035-scale-the-service-and-let-it-pick-the-instance.md), which raised the fleet from one task to four and moved the instance to `db.t4g.small` to hold them; the decision here is unchanged and only its inputs moved. Revised again on 2026-09-21 by [ADR-0043](./0043-a-deploy-dips-rather-than-doubles.md), which caps a deploy at the desired count so the task ceiling is four rather than eight and the pool goes from 20 to 45; the budget and its test are the same shape with one more input. Revised on 2026-09-23 by [ADR-0052](./0052-the-pool-keeps-a-warm-floor.md), which keeps five connections per task open in production; the ceiling is unchanged.

## Consequences

The unit test in `src/lib/__tests__/db-pool.test.ts` holds the sum (eight tasks at 20 plus 5, plus the one-off 10) to the 220 ceiling, so raising the pool, the task ceiling or the traffic share has to keep the inequality true or change the instance. The one-off 10 is a reservation rather than a measurement: `deploy.yml` waits for the migration task to stop before it updates the service, and `migrate()` uses one session, but the other scripts under `scripts/` open pg's default pool and can run at any time. Autoscaling past four tasks means a bigger instance or a smaller pool, not a silent overrun. The honest post-deploy signal is the hourly `DatabaseConnections` maximum staying below 20; pg-pool closes clients idle for 10 seconds, so a quiet task holds fewer, down to the five ADR-0052 keeps open. If it pins to 20, headroom is gone again and the cause wants diagnosing before another raise. `docs/QUIRKS.md` "Pool reuse" points here for the traffic writer exception.
